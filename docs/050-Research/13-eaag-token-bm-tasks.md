# Báo cáo #13 — EAAG token (token phiên trình duyệt) cho các endpoint Business Management

> Phạm vi: các loại token trích từ phiên web `business.facebook.com`/`facebook.com` (EAAG, EAAI, EAAE, EAAB...), cách trích chuẩn xác nhất tính đến **10/2026**, thời hạn sống & refresh, và **kiểm chứng thực tế** token phiên gọi được những endpoint Business Management nào (ưu tiên `POST /act_{ad_account_id}/agencies`, `/{asset}/assigned_users`, `/{pixel}/shared_accounts`, `GET /{business_id}/owned_ad_accounts|client_ad_accounts|business_users`). Kèm rate limit/lỗi khi gọi bằng EAAG.
> File này **bổ sung** — không lặp lại: file `04-bm-admin-assets.md` (catalog endpoint qua official API với app đã review), file `09-extension-techniques.md` (kỹ thuật extension nói chung), file `11-policy-compliance.md` (ToS/rủi ro), file `14-partner-assign-mapping-graphql.md` (GraphQL nội bộ cho tác vụ chỉ định partner).

---

## 1. Tổng quan

- "Token EAAG" là cách gọi phổ thông (cộng đồng VN/Indonesia) cho **user access token ngắn hạn mà Meta nhúng sẵn trong HTML/JS bootstrap** của các surface first-party (`business.facebook.com`, Ads Manager, `www.facebook.com`) để chính web client dùng gọi Graph API. Thực tế từ 2024–2026 quan sát thấy **nhiều prefix cùng tồn tại** tùy endpoint nhúng: `EAAG` (trang `business_locations`), `EAAI` (ajax bootloader endpoint của Ads Canvas), `EAAE` (trang `/accountquality`), `EAAB` (fallback scrape DOM / page-side).
- Token này là **token của app first-party của Meta** — không cần tạo Meta app, **không qua App Review**, nhưng cũng không thể `debug_token` về phía ta (không có app token của first-party app). Nó tương đương quyền của chính phiên web của user.
- Theo tài liệu Meta chính thức (đã fetch qua proxy reader, 12/10/2026): token web-login là **short-lived ~1–2 giờ**, "có thể thay đổi hoặc hết hạn sớm không báo trước". Từ token ngắn hạn lấy lại bằng cách **mở lại tab BM và trích lại**; không có server-side refresh (đổi long-lived cần app secret của app phát hành — không khả dụng).
- **Kết luận then chốt về khả năng gọi BM endpoints:** có bằng chứng open-source mạnh (đến 09/2026) rằng token trích từ phiên web **gọi được các endpoint đọc/ghi Business Management** như `POST /{business_id}/business_users` (invite), `GET /{business_id}/business_users` — vì web client BM thực chất gọi các edge này bằng chính token đó; riêng `GET /{business_id}/owned_ad_accounts` / `client_ad_accounts` dạng đứng riêng mới chỉ là suy luận chưa kiểm chứng trực tiếp (§2.2). Tuy nhiên **`POST /act_{id}/agencies` (chỉ định partner BM) bằng EAAG cụ thể là CHƯA XÁC MINH** — cần test thực tế (chi tiết §3).
- Đây là đường đi "nhanh" đúng yêu cầu, nhưng bản chất là dùng token sai mục đích thiết kế: rủi ro checkpoint tài khoản, vi phạm ToS → xem file 11.

## 3. Chi tiết kỹ thuật

### 3.1. Bản chất token & các vị trí nhúng (đã đối chiếu đa nguồn)

- Token nhúng trong **JSON bootstrap** server-rendered của trang BM: có thể nằm trong mảng JSON (`["...","EAAG...","..."]`), trong key `"apiAccessToken"`, `"accessToken"`, `"token"`, trong script tag inline, hoặc object global `bizKitSettingsConfig`, `__INITIAL_DATA__`, `__SERVER_DATA__` — danh sách pattern đầy đủ đã kiểm chứng trong `ntphong1501/Extension-Get-Token-EAAG/content.js` (regex ưu tiên có group-capture, validate `startsWith('EAAG')` + length ≥ 100 + charset `[A-Za-z0-9_-]`).
- **Route đáng tin nhất cho EAAG**: `https://business.facebook.com/business_locations` — cả 3 nguồn độc lập (extension VN 2025, scraper VN, tool Indonesia) đều dùng route này. Các route BM khác không đảm bảo nhúng token; nếu regex không thấy → mở route này.
- **Endpoint ajax** `bootloader-endpoint/?modules=AdsCanvasComposerDialog.react&__a=1` trả `"access_token":"EAAI..."` trong payload JSON — hiện là probe số 1 của toolkit 2026, vì "đó là token mà chính invite calls của web được authorize" (comment trong `goads-bm-invite.js`). Host: 2023–2024 ≈ `www.facebook.com`, 2026 ≈ `business.facebook.com` (so sánh SmitExt vs GOADS — host đã dời).
- Với **MV3 extension**: content script `document_end` + `MutationObserver` (SPA render muộn) + lưu `extractTime` để biết độ cũ (pattern của repo mẫu); probe module `require(...)` cần MAIN world (xem file 09 §3.1).
- Cookie `c_user`/`xs` cho phép server-side/tool ngoài `GET` `business_locations` rồi regex — **không khuyến nghị** (đánh cắp phiên, file 11).

### 3.2. Thời hạn sống, dấu hiệu hết hạn, refresh

**Thời hạn (nguồn chính thức, fetch 12/10/2026 qua r.jina.ai):**

> "Short-lived tokens typically last about **one to two hours**, while long-lived tokens last about **60 days**. Do not depend on these lifetimes remaining the same — they may change without warning or expire early." — Meta, guides/access-tokens.
> "Access tokens **generated via web login are short-lived**"; long-lived chỉ đổi được "by making a **server-side** API call with your **app secret**" → với token first-party ta **không thể** tự gia hạn (không có app secret của Meta).

- Kinh nghiệm cộng đồng VN ghi token BM "sống ngắn, phải lấy lại mỗi phiên" — khớp khung 1–2h; **con số chính xác từng loại (EAAG vs EAAI vs EAAE) chưa xác minh — cần test thực tế.**
- Token chết ngay khi: session web logout, đổi password (subcode 460), user bị checkpoint (459/464), hoặc admin/security revoke.

**Dấu hiệu hết hạn khi gọi Graph (docs chính thức, error-handling guide):**
| HTTP/code/subcode | Ý nghĩa | Xử lý |
|---|---|---|
| `OAuthException` code **190**, subcode **463** "Expired" / **467** "Invalid Access Token" / không subcode | Token hết hạn/thu hồi | Mở lại tab BM → trích token mới → retry **1 lần**; nếu vẫn 190 → fail-soft, báo user |
| subcode **460** Password Changed | User đổi mật khẩu | Bắt đăng nhập lại FB |
| subcode **459** User Checkpointed / **464** Unconfirmed User | Tài khoản bị checkpoint | **DỪNG automation**, warn user đăng nhập tay |
| code **102** (API Session) | Phiên chết | Như 190 |
| code **10** / **200** | Thiếu quyền trên object cụ thể | Không retry; báo thiếu quyền trên BM/asset đó |
| `suppress_http_code=1` | Graph trả HTTP 200 kèm `error` trong body | Pattern tool 2026 dùng để parse lỗi thống nhất (goads) |

- Không dùng được `/debug_token` về phía mình (cần app token của app phát hành token). **Cách rẻ nhất để check sống/chết: `GET /me?fields=id`** — read = 1 điểm theo khung rate chính thức; lỗi 190 = hết hạn.

**Refresh tự động (khuyến nghị kỹ thuật):** extension giữ token trong `chrome.storage.session` kèm `extractTime`; trước mỗi batch ghi, probe lại tab BM đang mở (`chrome.tabs.query` url `business.facebook.com/*` → `chrome.scripting.executeScript` để get token mới nhất); nếu không có tab BM → mở tab mới vào `business_locations` (hoặc bắn fetch bootloader-endpoint từ chính tab). Pattern "extract-on-demand mỗi lần act" là cách tool 2026 vận hành (goads probe lại token ngay khi user nhấn action; bm-approve có hằng số timeout 25s, delay giữa approvals 500ms).

### 3.3. Kiểm chứng `POST /act_{ad_account_id}/agencies` — trạng thái 10/2026

- **Docs mới** (mirror `emeraldtarek/meta-ads-api-docs-md`, snapshot 2026-04-26 theo README nguồn, selector version v22–v25, trang `ad-account/agencies`): **Reading (GET) + Deleting (DELETE `{business}`) có ghi đầy đủ; mục Creating để trống**, summarized ghi rõ "CREATE and UPDATE are not supported". Error codes liệt kê: 190, 200, 100, **80004**.
- **Nhưng chính các trang reference mới** (mirror snapshot 2026-04-26, theo README nguồn — `business/owned_ad_accounts` cập nhật 24/02/2026 và `business/client_ad_accounts`, nguyên văn giống nhau) khẳng định: "At the end of September 2024, the `POST /{pixel-id}/shared_accounts` API ... will not support sharing of pixels with an ad account, if a business account does not have access to both pixel and ad account. Refer to the pixel sharing API solution to use `POST /{pixel-id}/agencies` **or use `POST {ad_account}/agencies` to share into a business account**, then use `POST /{pixel-id}/shared_accounts` to link pixel and ad account." → Meta **tự tham chiếu `POST {ad_account}/agencies` là flow hiện hành** ngay trong docs tháng 02/2026 dù mục Creating của trang `ad-account/agencies` để trống. Riêng guide `business-asset-management/guides/business-pixel-sharing` còn sống (fetch 10/2026) mô tả flow pixel: `POST <ads_pixel>/agencies` (step 1, "system user that owns the Pixel") → `POST {request_id}?request_status=APPROVE` (step 2) → `POST <ads_pixel>/shared_accounts?business&ad_account` (step 3) → `DELETE <adspixel>/agencies` (step 4).
- **Thực tiễn production**: `hhavey275-code/crmsoftit-0fc5a843` (Supabase CRM, 04/2026) implement "add partner" bằng chuỗi 3 method: (1) `POST /{owner_bm}/managed_businesses` `existing_client_business_id`; (2) `POST /{owner_bm}/client_ad_accounts` `adaccount_id, permitted_tasks, business`; (3) **`POST /v25.0/{actId}/agencies` `business, permitted_tasks`** — code cho thấy endpoint vẫn được dùng thực tế với user token OAuth (app riêng của họ), và tác giả phải fallback vì từng method fail tùy quan hệ/permission.
- **Với EAAG cụ thể: CHƯA XÁC MINH.** Không tìm được code mở nào chứng minh/thất bại khi gọi `/agencies` bằng token phiên. Suy luận: vì token phiên chính là token web client BM dùng, xác suất cao POST thành công khi user có quyền admin trên BM sở hữu ad account; nhưng phải test thực tế (cùng với `assigned_users`, pixel `agencies`/`shared_accounts`).
- Volume phát hiện: dù token chết được endpoint, flow "share vào BM khác" vẫn có thể tạo **sharing agreement pending** phía BM nhận (như pixel flow: trả `pending_request_id`) — extension phải xử lý trạng thái pending, không phải coi success={true} là xong (theo guide pixel-sharing step 1–2).

### 3.4. Rate limit & lỗi khi gọi bằng EAAG (khác token app ra sao)

**Khung chính thức** (mirror docs `marketing-api/overview/rate-limiting`, bản trong snapshot mirror 2026-04-26 theo README nguồn):

- Đếm điểm: read = 1 điểm, write = 3 điểm; chạm trần → throttling error.
- Các mã chính: **4** (`Application request limit reached`, sub 1504022/1504039) app-level; **17** (`User request limit reached`, sub 2446079) user-level; **613** (sub 1487742 "too many calls from this ad-account", sub 5044001 mutation/QPS per ad account ≈ 100 QPS); **80000/80003/80004/80014** (Business Use Case per ad account — header `x-business-use-case-usage`); sub riêng cho budget change (1487632), spend limit 10 lần/ngày (1885172).
- Endpoint error tables riêng: `agencies`: 190/100/200/80004; `assigned_users`: 100/200/**2620** "Invalid call to update account permissions"; `shared_accounts`: 100/190/200.

**Khác biệt thực tế khi gọi bằng EAAG** (suy luận từ cơ chế + thực nghiệm cộng đồng, chưa kiểm chứng độc lập):

- **App-level (code 4) gần như không bao giờ chạm**: token thuộc first-party app (web BM) có quota nội bộ khổng lồ; đồng thời EAAG **bypass hoàn toàn khái niệm Standard/Advanced Access** của app thường — tài liệu authorization ghi Standard Access "Limited access to Business Manager ... APIs. **No Business Manager access** to manage ad accounts, user permissions and Pages", trong khi token phiên web vẫn gọi được các edge này (đã kiểm chứng §2.2). Đây chính là giá trị cốt lõi của hướng EAAG.
- **Ràng buộc thực là user-level (code 17) và ad-account/BUC-level (613, 80004)** — giống hệt token app; header `x-ad-account-usage`, `x-business-use-case-usage` vẫn trả về bình thường (nhận định cần confirm trên phiên thật).
- Thực tiễn throttle trong tool mở: `goads-bm-approve` dùng `DELAY_BETWEEN_APPROVALS_MS = 500`, paging tối đa 10 trang × 20, timeout 25s → khuyến nghị từ **~2 request ghi/giây trở xuống** + backoff theo header/estimated_time.
- **Lỗi đặc thù token phiên**: ngoài bảng ở §3.2, pattern gọi từ IP/thiết bị khác session web (hoặc tần suất batch mạnh) kích hoạt checkpoint → token/tài khoản chết theo cụm 459/464 (rủi ro chi tiết → file 11).

### 3.5. Ghi chú version & tương thích

- Toolkit 2026 pin **v19.0** cho invite (`business_users`) và batch fallback trỏ `relative_url` tới **/v3.0** — **lưu ý cả hai version này thực tế đã quá hạn** theo lịch sundown (v20 đã hết hạn 24/09/2026; v19, v3.0 còn lâu trước đó — xem file 01 §1) nên việc chúng vẫn gọi được là **bằng chứng Meta nới lỏng hơn policy ở các edge BM này** (legacy endpoints sống lâu hơn lịch công bố), chứ không phải "đúng chính sách ~2 năm/version". Khuyến nghị extension dùng **v26.0** khi viết code mới; chỉ replay nguyên văn version cũ nếu copy flow đã kiểm chứng của tool khác.
- Parse lỗi nên hỗ trợ cả hai dạng response: HTTP 4xx chuẩn và `suppress_http_code=1` (HTTP 200 + JSON `{error}`).

## 4. Khuyến nghị cho extension (hpma-extension)

1. **Kiến trúc token**: content script trên `business.facebook.com` probe theo chuỗi 3 bước §2.1 (EAAI bootloader → `require("WebApiApplication")` qua MAIN world → scrape EAAG/EAAB), lưu `chrome.storage.session` + `extractTime`; refresh-on-demand trước mỗi batch (mở/focus tab `business_locations` nếu token > ~45 phút hoặc sau lỗi 190 đầu tiên — ngưỡng thực nghiệm, tinh chỉnh sau test).
2. **Ưu tiên tác vụ theo mức kiểm chứng**: làm trước lớp đọc kiểm kê đa-BM (`me/businesses`, `business_users`, `owned/client_ad_accounts`, `verification_status`) và invite user (`POST business_users` + batch fallback — đã kiểm chứng 2026). `POST /act_/agencies`, `assigned_users`, pixel sharing: **đánh dấu "beta — cần test trên tài khoản thật"**, implement sau khi có kết quả test; nếu live-test fail thì degrade sang hướng dẫn deep-link Business Settings như file 04 §4.
3. **Xử lý lỗi bắt buộc**: map đầy đủ bảng §3.2 + §3.4 (đặc biệt 190×463/467 → refresh; 459/464 → dừng hẳn automation + cảnh báo checkpoint; 17/613/80004 → backoff; 2620 → thiếu quyền trên account). Retry ghi tối đa 1 lần sau refresh token; không retry khi 200/10.
4. **Hỗ trợ hai kiểu response** (suppress_http_code) và **trừ điểm paging** (`paging` chứa token — không log, theo cảnh báo của `facebook-data-extraction`).
5. **Bảo mật**: không truyền token ra server (anti-pattern thực tế: `SmitExt` có bản `extension_v2/remote`, `crmsoftit` lưu token BM trên Supabase — không bắt chước); không log token; không đính token trong URL khi có thể đưa POST body (tool 2026 vẫn để `access_token` trong query string — chấp nhận được cho tính tương thích nhưng extension nên ưu tiên body); dọn token khi logout/đóng tab cuối của BM. ToS & rủi ro checkpoint → file 11 (token phiên = full quyền web session; Meta phát hiện qua lệch pattern; 252 GitHub issues hiện chứa EAAG bị rò rỉ — minh chứng token là secret cấp session).
6. **Test plan tối thiểu trước khi ship** (điền vào cột "chưa xác minh"): một BM thật, admin thật — (a) `GET /me` check token; (b) `GET /{bm}/owned_ad_accounts`, `client_ad_accounts`, `business_users`; (c) `POST /act_test/agencies` với BM phụ; (d) `POST /act_test/assigned_users`; (e) `POST /{pixel}/shared_accounts`; ghi lại: HTTP, error code/subcode, headers usage — cập nhật lại §2.2 sau test.
