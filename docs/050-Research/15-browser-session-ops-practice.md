# 15 — Thực hành & rủi ro thực tế khi chạy tác vụ BM bằng token phiên/session trình duyệt (không qua App Review)

> Phạm vi: **vận hành thực địa** — cách các tool hiện có trên thị trường làm tác vụ "chỉ định đối tác / share tài sản BM" mà KHÔNG cần Meta App + App Review; rủi ro thực tế từng cơ chế; kinh nghiệm giảm rủi ro từ cộng đồng/tool VN & hệ sinh thái antidetect; checklist vận hành an toàn cho extension của mình.
> Không lặp lại: chi tiết endpoint official API (xem `04-bm-admin-assets.md`), kỹ thuật trích EAAG/intercept GraphQL/DOM automation (xem `09-extension-techniques.md`), cảnh quan đối thủ đầy đủ (xem `10-existing-tools.md`), khung pháp lý/ToS (xem `11-policy-compliance.md`). File này chỉ đi sâu vào **thực hành vận hành bằng token phiên** và **đánh giá rủi ro theo tác vụ**.
> Thời điểm nghiên cứu: **2026-10-12**. Graph API mới nhất: **v26**.

## 1. Tổng quan

**Cơ chế của toàn bộ thị trường "tool BM không cần app review" quy về đúng 3 mô hình kỹ thuật** (đã kiểm chứng bằng tài liệu first-party của chính các tool):

| --- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| M1  | **Session-token → Graph API từ trình duyệt người dùng**      | Extension đọc phiên đăng nhập (`cookie` c_user/xs hoặc token EAAG nhúng trong HTML của `business.facebook.com`), rồi từ chính trình duyệt đó gọi `graph.facebook.com` / `business.facebook.com` | **BMTool.vn** (web app + extension), Ads Helper, AdsSuite, Fast Invite BM — toàn bộ trên Chrome Web Store   |

**Phát hiện then chốt về M1 (cơ chế mục tiêu của chúng ta):**

- BMTool.vn **công khai trên Chrome Web Store** (bản 1.7.2, cập nhật 09/07/2026, 29.61 KiB, rating 5.0) và **tự mô tả cơ chế ngay trong listing**: _"BMTool sử dụng phiên đăng nhập Facebook của chính bạn (trên trình duyệt) để gọi các API chính thức của Facebook (graph.facebook.com, business.facebook.com)"_. Privacy policy (cập nhật 05/06/2026) khẳng định phiên/cookie/token **"được sử dụng để gọi trực tiếp tới máy chủ Facebook... chủ yếu xử lý ngay trên trình duyệt"**. → Tức là: **token phiên + gọi Graph API ngay từ browser của user (cùng IP, cùng fingerprint)** là cơ chế được "legitimize" lên tới mức vượt review Chrome Web Store.
- Extension **Ads Helper** (CWS) tự mô tả: _"Facebook token, session cookies and ad account status. Requests go only to graph.facebook.com, with built-in rate limits."_ → bằng chứng thứ hai độc lập rằng M1 tồn tại công khai, và **rate-limit client-side là tính năng bán hàng** chứ không phải bí quyết.
- Lý do kiến trúc "chạy trong browser thay vì server": request mang token gọi từ **cùng IP + cùng thiết bị với phiên đang login** nên ít lệch chuẩn nhất về mặt tín hiệu rủi ro (IP/device mismatch là tín hiệu checkpoint hàng đầu — xem §3.1).

**Về ranh giới "được phép — vi phạm":** M1 về bản chất vẫn là _dùng token sai mục đích thiết kế_ (token của app web nội bộ Meta) — về ToS xem file 11. Nhưng thực tế thị trường VN đã vận hành ở quy mô lớn nhiều năm với tỉ lệ chết sản phẩm cao (file 10 ghi nhận loạt domain chết: maxcare.vn, phanmemninja.com, bigbom.com...; riêng GPM-Login — được file 10 ghi nhận còn sống — probe ban đầu ngày 12/10/2026 nhầm domain `gpm-login.com` (NXDOMAIN); domain đúng **`gpmlogin.com` vẫn resolve bình thường** khi kiểm tra từ máy nghiên cứu → rút kết luận "đã chết"; cần probe lại first-hand trên môi trường research). Bài học: mô hình này _sống được_ nhưng _giòn_, cần thiết kế fail-soft và kỳ vọng rõ với người dùng.

### 2.2. Cách M1 thực thi tác vụ partner/share (tái cấu trúc từ bằng chứng + file 09)

1. **Cấp phiên:** content script trên `business.facebook.com` trích EAAG token từ HTML/script inline (kỹ thuật chi tiết — file 09 §3.3; repo mẫu `ntphong1501/Extension-Get-Token-EAAG`), hoặc dùng `chrome.cookies` (khi ext khai quyền) cho nhóm tool cookie-based.
2. **Gọi API từ browser:** `fetch('https://graph.facebook.com/v26.0/act_{id}/agencies', {method:'POST', body: business=B_id&permitted_tasks=[...] &access_token=EAAG})` **chạy trong context của trình duyệt đang login** → request mang IP/User-Agent trùng với phiên web. Đây chính là khác biệt mấu chốt so với "get token rồi gọi từ server" (mô hình cũ, dễ chết).
3. **Khung vận hành:** web app điều phối (dashboard, hàng đợi, báo cáo), extension thực thi; batch share được cấu hình "Luồng/Delay tùy chỉnh" (BMTool trang chủ) — tức song song nhiều phiên FB nhưng mỗi hành động có delay.
4. **Lặp qua nhiều "phiên FB":** nền tảng như BMTool có khái niệm "Phiên FB" riêng trong dashboard (menu `/hotro`: "BM · Phiên FB · Tài khoản") — mỗi phiên = 1 tài khoản FB đang đăng nhập; người dùng gắn nhiều phiên để chạy bulk cross-BM.

### 2.3. Điểm các tool KHÔNG làm (để tránh lạc quan)

- Không tool nào (công khai) tự động **accept invite phía nhận** ở quy mô lớn được "hợp lệ hóa" — tác vụ có bên kia con người (file 04 đã chỉ ra "hybrid flow"); Fast Invite BM chỉ hỗ trợ bulk-accept _links dán tay_ (resumable), tức vẫn semi-manual.
- Không tool session nào làm **system user token / app review flows** — bản chất các tác vụ đó cần app Meta thật (file 04 §3.3).
- Tác vụ **payment/appeal/business verification** vẫn là "no-go" thống nhất giữa cả 4 tài liệu của team (04/09/10/11) — không chồng lấn ở đây.

## 3. Rủi ro thực tế từng cơ chế (b) — tín hiệu Meta flag & tỉ lệ rủi ro theo tác vụ

## 4. Checklist vận hành an toàn khi triển khai cho extension (c)

Thiết kế cho repo `hpma-extension`, bám sát cơ chế M1 + gợi ý "learn-then-replay" ở file 09.

**A. Pre-flight (trước khi chạy batch):**

1. Kiểm tra **sức khỏe phiên**: token còn hạn (`GET /me?fields=id,name` + `debug_token`-style probe), session vừa mở từ tab BM thật (fallback theo file 09 ưu tiên 2).
2. Kiểm tra **sức khỏe tài sản** trước khi ghi: `GET /{business_id}?fields=verification_status,created_time`, `GET /act_{id}?fields=account_status,disable_reason` — **chặn tác vụ ghi lên BM/TKQC vừa tạo (< ~2 tuần — heuristic cộng đồng) hoặc đang PENDING_RISK_REVIEW/UNSETTLED**; cảnh báo đỏ cho BM chưa verify.
3. Xác nhận **quyền actor**: user phải là ADMIN của BM nguồn (đọc `/business_users`), nếu không fail sớm thay vì 200-error giữa chừng.
4. Ping **rate-limit headroom**: đọc header `x-business-use-case-usage`/`x-ad-account-usage` sau vài call đầu; dừng khi >70% (theo file 04 §3.4).
5. Xác nhận **môi trường ổn định**: không chạy ngay sau khi user đổi IP/đổi thiết bị; nếu extension phát hiện UA/IP mới lạ so với lần trước → cảnh báo "hãy dùng thủ công 1–2 ngày trước khi batch".

**B. Trong khi chạy:** 6. **Dry-run mặc định**: render bảng diff (TKQC × partner × permitted*tasks), user bấm "Chạy thật" mới ghi. (Đồng bộ khuyến nghị file 04 §4.) 7. **Human-in-the-loop cho write nhạy cảm**: confirm 2 lớp cho DELETE và cho batch > N phần tử (N mặc định 10). 8. **Pacing**: delay cố định nền 3–8s + **jitter ngẫu nhiên** giữa mọi write; gom đọc bằng Batch API (≤50 req/batch) nhưng **không batch write nhạy cảm** (batch làm mất dấu chân tay người — heuristic [anecdotal]). 9. **Giới hạn theo ngày (community heuristic [anecdotal], tinh chỉnh theo thực địa):** BM mới/ít lịch sử: **≤5–10 partner-adds/ngày/BM**; BM "cứng" (≥3 tháng, có spend, verified): ≤20–50; giới hạn share pixel tương đương; tổng write/ngày/actor ≤ ~100. Đây là khung khởi đầu bảo thủ, tham chiếu số warm-up của Hidemyacc (5–10 action/ngày tuần đầu). 10. **Thứ tự thao tác**: đọc trạng thái hiện tại (`GET /act*{id}/agencies`) → bỏ qua mục đã tồn tại (idempotent) → ghi từng cái một → re-read xác nhận. Tránh vòng lặp retry vô hạn khi 403/190/80004 — **fail-soft: dừng batch, báo user** (đồng nhất với file 09 khuyến nghị fail-soft). 11. **Dừng khẩn cấp** khi gặp: mã 190 (token die), checkpoint UI xuất hiện trên tab, 3 lỗi 80004/17/613 liên tiếp, hoặc header usage vọt → pause toàn bộ queue, hiện banner "Meta đang siết — nghỉ X giờ". Riêng **error 200 = thiếu quyền (permissions), KHÔNG phải tín hiệu rate-limit/checkpoint**: fail-sớm với thông báo thiếu quyền, không tính vào logic dừng khẩn cấp.

**C. Audit & rollback:** 12. **Append-only audit log** (options page, export CSV): thời điểm, actor phiên, endpoint, payload ẩn token, kết quả Meta trả về (id), lỗi. Meta có Setting Log phía BM (file 04 #29) nhưng log nội bộ cho phép phản hồi nhanh khi user bị hỏi. 13. **Undo path dựng sẵn**: mọi hành động `POST /act_{id}/agencies` sinh ra "undo instruction" = `DELETE /act_{id}/agencies {business}`; màn hình "Hoàn tác batch gần nhất" → gọi undo với cùng pacing. (Mirror docs xác nhận DELETE trả `{success:true}`.) 14. **Không export cookie/token ra ngoài** (đồng nhất file 09 §3.4 & file 11); báo cáo chỉ chứa ID/URL/job-hash, không chứa phiên.
